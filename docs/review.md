## 強み

### 1. レイヤー分離が明確で一貫している

```
Framework (src/Framework/)
  ↑
Shared (apps/shared/)
  ↑
├── CMS (apps/cms/)
└── Front (apps/front/)

Kernel (apps/kernel/) ← 全体のコンポジション担当
```

依存方向が単方向に保たれており、どこに何を書くべきかが明確。Framework が HTTP プリミティブと DI のみを持ち、ドメインロジック・永続化・テンプレートエンジンの選択をアプリケーション層に委ねる設計は、フレームワークの責務として適切に絞られている。

### 2. フレームワークが意図的に薄い

わずか 28 ファイル。提供するものと提供しないものが `src/Framework/README.md` に明文化されており、「このフレームワークが所有しないもの」リストが存在することは設計意図の明確さを示す。過剰な抽象化を避け、削除・置換のしやすさを優先する姿勢は長期保守性に寄与する。

### 3. ユースケースパターン (Input / Interactor / Output) が統一されている

```
Application/{Feature}/{UseCase}/
├── Input.php
├── Interactor.php
└── Output.php
```

Controller がビジネスロジックを持たず、Interactor への委譲に徹している。これにより Controller は薄く保たれ、ビジネスロジックが単独でテスト可能になっている。Query と Repository を分離し、読み取りと書き込みの関心を区分しているのも良い判断。

### 4. PSR の採用が選択的かつ合理的

PSR-3 (ログ)、PSR-4 (オートロード)、PSR-11 (DI)、PSR-16 (キャッシュ) を採用しつつ、PSR-7 (HTTP) は採用せず独自実装を選択している。「エコシステム互換性よりシンプルさ」という判断の根拠が README に記載されており、言い訳なく設計判断として成立している。

### 5. PHPStan レベル MAX

`phpstan.neon` で `level: max` を設定していることは、型安全性への強いコミットメントを示す。PHP 8.5 を要求していることも、最新の言語機能を活用できる環境として評価できる。

### 6. コンテンツバージョニングと Audit 基盤の存在

`article_versions` / `page_versions` テーブルによるスナップショット、`AuditLoggerInterface` の存在は、メディアサイトとして必要な「誰がいつ何を変更したか」の追跡基盤が考慮されていることを示す。

### 7. セキュリティの基礎が Middleware で整備済み

- `SecurityHeadersMiddleware` (CSP、Referrer-Policy、Permissions-Policy)
- `CorsMiddleware`
- `Csrf` (Framework レベル)
- `RequireCmsSessionMiddleware` (CMS 認証ガード)
- HTML サニタイズ: `ezyang/htmlpurifier`

セキュリティ上の基本ヘッダーがミドルウェアとして注入される設計は、追加・差し替えが容易であり適切。

### 8. スキャフォールドツールによる一貫性の強制

`bin/scaffold-kernel`、`bin/scaffold-app`、`bin/scaffold-shared` が存在し、新機能追加時のアーキテクチャ逸脱を防ぐ仕組みが整備されている。`--template=layered` オプションが Use Case の雛型を生成するのも実用的。

## 課題・懸念点

### 1. テスト密度が低い (最大の懸念)

**評価: 4.5 / 10**

22 個のテストファイルが存在するが、実際のテスト数は約 13 テスト・25 アサーションと、システムの規模に対して著しく不足している。

- CMS の記事 CRUD・バージョニング・メディアアップロードに対するテストがほぼ皆無
- Front の検索・ページネーション・カテゴリ/タグ表示に対するテストが薄い
- データベース統合テスト (実 DB を使うもの) が存在しない
- Interactor 単体テストが不足しており、PHPStan で型は保証されていてもビジネスロジックの正しさが保証されていない

PHPStan MAX は型エラーを防ぐが、ロジックの正確性は保証しない。テスト不足はリグレッションリスクを高める。

### 2. 例外ハンドラのデフォルトが本番非想定の動作

`RethrowingExceptionHandler` がデフォルトであり、これはスタックトレースをそのままユーザーに露出する可能性がある。プロダクション環境でカスタムハンドラの注入を忘れた場合、内部情報が漏洩するリスクがある。`APP_ENV` による自動切り替え、もしくはデフォルトを安全側 (プレーンテキスト 500) に変更することが望ましい。

### 3. Front のキャッシュ戦略が不明確

`FileSimpleCache` (PSR-16) の実装は存在するが、Front の記事一覧・詳細ページでのキャッシュ適用が薄い。読み取り中心のメディアサイトとして、人気記事やカテゴリ一覧のキャッシュは重要なパフォーマンス施策となりうる。ファイルベースキャッシュは単一サーバーでは機能するが、スケールアウト時の課題となる。

### 4. 全文検索がデータベース依存

`Article/Search` が存在するが、実装が PostgreSQL の全文検索 (もしくは LIKE 検索) に依存していると想定される。データ量が増えた場合のパフォーマンス劣化が懸念される。Meilisearch・Elasticsearch 等の専用検索エンジンへの移行パスを検討する価値がある (将来の課題として)。

### 5. メディアファイルが `public/uploads/` に直置き

画像・動画が `public/uploads/media` に保存されている。この設計では:
- Web サーバーが直接配信するためアクセス制御が困難
- CDN 分離が容易でない
- ストレージスケールアウト時の移行コストが高い

プロダクション要件が高まった際は、オブジェクトストレージ (S3/R2) + CDN への移行を検討すべき。

### 6. 問い合わせフォームのレート制限が不明

`Inquiry/Create` (お問い合わせフォーム) に対するレート制限・スパム対策 (CAPTCHA 等) が確認できない。CSRF トークンは存在するが、同一ユーザーからの連続送信を防ぐ仕組みがない。

### 7. Audit ログの実装結合が未確認

`AuditLoggerInterface` は存在するが、CMS の実際の操作 (記事の保存・削除・メディアアップロード等) にどの程度バインドされているかが不明。インターフェースが存在するだけでは機能しない。

### 8. PSR-7 非採用 ── 意図的な設計判断として妥当

独自 `Request`/`Response` の採用は意図的な選択であり、課題ではない。

PSR-7 は `StreamInterface`、`withXxx()` による immutability、複雑なメッセージインターフェース階層など設計上の複雑さが大きく、「サードパーティライブラリの接続口として機能させる」目的がない場合にその複雑さを引き受けるメリットは存在しない。自前の HTTP 層は必要な分だけ複雑で済み、削除・置換も容易である。このシステムの「Explicit over Magic」という哲学と完全に一致した判断と評価する。

## 設計哲学への評価

このシステムが採用する「Explicit over Magic」の哲学は、小中規模のウェブメディアに対して正しい選択だと評価する。

Laravel や Symfony を採用した場合と比較して:
- **利点:** フレームワーク更新に引きずられない、依存が少ない、学習コストが低い、削除・置換が容易
- **欠点:** ORM・認証・キュー等の標準機能は自前実装が必要、エコシステムの恩恵を受けにくい

この判断が正当化されるのは「自作フレームワークの開発そのものが目的の一部である」場合、もしくは「特定の設計上の制約が強い場合」であり、このプロジェクトはその条件を満たしている。

## 改善推奨事項 (優先度順)

| 優先度 | 項目 | 概要 |
|--------|------|------|
| 高 | テスト拡充 | Interactor 単体テスト、DB 統合テスト (テスト用 DB) の追加 |
| 高 | 例外ハンドラのデフォルト変更 | `APP_ENV=production` 時に安全なハンドラへ自動切り替え |
| 中 | レート制限の追加 | お問い合わせフォームへの送信頻度制限 |
| 中 | キャッシュ適用 | 記事一覧・詳細の結果をキャッシュし DB 負荷を軽減 |
| 中 | Audit ログの結合確認 | CMS 操作への実際のバインドを確認・補完 |
| 低 | メディアストレージ抽象化 | ファイルシステム依存をインターフェース化して将来の移行を容易に |
| 低 | 全文検索の外部化検討 | データ増加時の備えとして検索エンジン分離の設計検討 |

## 結論

このシステムは、設計哲学の一貫性・レイヤー責務の明確さ・保守性において高く評価できる。特に「フレームワークが所有しないものを明示する」姿勢は、多くの自作フレームワークが陥りがちな責務膨張を回避している点で優れている。

一方で、テスト密度の低さは現時点での最大の技術的負債であり、機能が増えるにつれてリグレッションリスクが累積する。PHPStan MAX という静的解析の厳格さとテストの手薄さのギャップを埋めることが、次の優先投資先となる。

ウェブメディアの公開基盤として機能する成熟度は持っているが、長期的な安定運用に向けてテストと一部のプロダクション安全策の整備が必要な段階にある。
